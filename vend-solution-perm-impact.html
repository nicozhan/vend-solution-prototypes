租户权限上线影响评估

基于「租户只能看到自己的产品、配方、原料」这条硬规则，评估它对现有租户、机器、权限与用户体系的影响，以及上线前必须先定下来的决策点。

评估对象 租户权限模块（功能权限 × 机器范围） 新增约束 产品 / 配方 / 原料 数据隔离 日期 2026-11-06
一句话结论

这条规则不是给权限页加一个「数据范围」开关，而是给全平台补一条数据归属主线。真正的工作量不在权限配置页，而在存量数据的归属补齐、所有查询出口的统一拦截，以及机器归属转移时产品/配方怎么跟着走这三处。建议先只做「看不见别人的」，授权共享放到第二期灰度。

01

先把「自己的」定义清楚

现在有三种租户，同一个产品对它们的含义并不相同。如果不区分「拥有」和「被授权使用」，规则落地后运营商侧会直接变成空列表 —— 它拿不到工厂的产品，就没法给机器上架商品。

工厂
拥有：产品 / 配方 / 原料
配方是工厂的核心资产，投料比例、工艺参数属于最敏感数据。
运营商
被授权使用：产品规格
需要知道卖什么、怎么出杯、价格与库存；通常不需要看到配方明细。
子运营商
继承运营商的授权范围
不能超出上级的品牌与产品授权，同样不该看到上游配方。
数据对象工厂运营商 / 子运营商平台
产品（SPU/SKU） 拥有 自己创建的、品牌授权范围内的 被授权 只看分配给自己的产品；授权撤回即不可见 全部可见，查看留审计
配方 拥有 明细、版本、成本 默认不可见 只看到成品规格；如业务需要，可开「允许授权租户使用（不下发明细）」 建议默认脱敏，看明细需二次确认 + 水印
原料 拥有 生产用料、供应商、批次 自己的 自采耗材（杯盖、糖包、清洁剂）与工厂原料不能共用同一个库 全部可见
02

权限模型的判断顺序要变成四层

现在的模板是「功能权限 × 机器范围」取交集。加上数据隔离后，判断必须按下面的顺序逐层收窄，任何一层为空结果就是空，不能靠前端隐藏。

L1 · 硬边界
租户隔离
tenant_id 必须在数据层强制注入，任何角色都越不过
→
L2 · 软收窄
用户数据范围
当前租户 / 指定范围 / 含授权子租户
→
L3 · 功能
功能权限
能不能进这个页面、能不能改
→
L4 · 对象
机器范围 × 数据范围
看得到哪些机器、哪些产品/配方/原料

注意 L3 和 L4 是并列的两个维度：只给「产品管理」功能权限、不给数据范围，用户会进入一个空列表；反过来给了数据范围没给功能权限，则入口都进不去。这两个维度要在模板里分开配置，并在保存时校验，避免做出「有入口没数据」或「有数据没入口」的废模板。

03

对现有模块的六处直接影响

按影响从大到小排列，前三条会改到已经定稿的交互。

3.1

机器归属转移

影响最大

机器转归属是目前唯一会跨租户搬动资产的流程，产品与配方会跟着机器一起被质疑「归谁」。

  • 所有权转移（工厂卖给运营商）：机器上在售的产品授权应随之转移，原工厂对该机器变只读 —— 和现在「工厂变只读」的规则一致，但要补一句「产品与配方授权同步转移」。
  • 仅管理权转移（代管）：产品授权不变，机器仍用工厂的产品；运营商自己的配方与原料不进这台机器。
  • 转移抽屉第二步需要多一个「随机器转移的产品清单」确认块，否则转移后运营商的机器上商品全部失效。
  • 边界情况：机器上挂着已停用/已收回品牌的产品时，转移要拦截或提示先换品。
3.2

租户权限（权限模板）

影响最大

模板从两个 Tab 变成三个维度，且「复制」功能会出现新的越权风险。

  • 机器范围 Tab 已有「指定机器」，产品/配方/原料如果也支持「指定范围」，模板里存的是具体数据 ID；跨租户复制时这些 ID 在目标租户并不存在，直接复制就是越权。
  • 建议模板只存范围规则（如「本租户全部」「本租户 + 授权下级」），不存数据 ID 清单；确需指定时，复制后强制进入「重新指定」状态，标记为待确认。
  • 功能权限树里新增节点时，要和数据范围联动提示：勾了「配方管理」但数据范围是「无配方」，保存时给警告而不是静默通过。
3.3

品牌授权

影响最大

品牌授权是产品可见范围的硬上限，两者是包含关系，不是并列关系。

  • 租户可见产品 = 品牌授权 ∩ 产品归属/授权。收回品牌后，该品牌下产品立即不可见、不可绑定新机器。
  • 已经在机器上售卖的产品如何处理需要明确策略：建议「保留售卖、禁止新增、页面标注品牌授权失效」，而不是直接下架，避免机器停摆。
  • 新建租户时 03 品牌授权选了「全部品牌」，要确认这个「全部」是当前全部还是含未来新增品牌 —— 后者会让产品可见范围随时间自动扩大，容易出事故。
3.4

租户列表与统计口径

中等
  • 列表现在展示「设备数量 / 用户数量」，加上产品/原料数量后，统计本身也会泄密：能从数量反推对手有多少配方。建议平台侧只对平台角色展示，租户视角只展示自己的。
  • 高级筛选里的「环境 / 状态 / 品牌」等条件，组合起来同样可以试探出别的租户是否存在某种产品，需要限制为只能筛自己的。
3.5

用户列表（数据范围字段）

中等
  • 用户已有「数据范围：当前租户 / 指定范围 / 当前租户 + 授权子租户」，这条是租户内的软过滤，永远不能突破 L1 租户隔离。
  • 两种范围叠加后要给出可读的结果：例如「工厂 A 的用户，数据范围含授权子租户」只能看到工厂 A 自己 + 被授权的下级运营商数据，看不到其他工厂。
  • 批量建号时的默认数据范围建议固定为「当前租户」，不要继承创建者的范围，否则批量建出来的账号权限会莫名放大。
3.6

远程托管（平台代维）

中等
  • 托管是以租户 admin 身份进入，配方页会成为整条链路最敏感的页面：建议配方详情进页面时二次确认、页面加水印（操作人 + 会话号 + 时间）、并强制写审计。
  • 托管期间的导出应默认关闭，或导出文件带水印与来源标记。
04

最容易漏掉的七个点

这些不是「产品设计」问题，而是上线后最常被拿来验证的漏洞口子。

4.1

所有出口要共用一套过滤

高

列表、详情、导出 Excel、全局搜索、下拉选择器（选产品、选原料、选机器）、报表看板、消息通知、打印/分享链接、开放 API —— 只要有一处是各页面自己写的过滤条件，就一定会漏。建议在数据访问层统一注入，页面不留手写 where。

4.2

编码唯一性会从全局变租户内

高

SKU 编码、原料编码原来是全局唯一，加了租户后必须改成 (tenant_id, code) 复合唯一。这一步是数据库层面的破坏性变更：按 code 查询会返回多条、历史外部对接的编码假设会失效，需要提前和对接方确认。

4.3

存量数据没有归属

高

已上线的产品/配方/原料没有 tenant_id 字段。上线前必须做一次归属补齐（按品牌、按机器、按创建人推断），并导出一份「无法判断归属」的清单人工确认。否则结果只有两种：全部看不见，或者互相可见 —— 后者是数据事故。

4.4

缓存与搜索索引

中

如果产品/配方用了 Redis 缓存或 ES 搜索，key 与索引都必须带 tenant_id，并且搜索引擎的过滤要在查询层做，不能查回来再在应用层筛。

4.5

一个用户属于多个租户

中

现在用户是单租户。如果以后支持跨租户（同一个人既在工厂又在运营商），登录后必须有「当前租户」上下文，切换租户要重新签发会话，否则权限会串。

4.6

租户停用 / 删除后的数据

低

租户被禁用后其产品是否还能被机器引用、被下级引用；租户删除后配方与原料是软删保留还是物理清理。建议：软删 + 观察期，被引用中的对象禁止物理删除。

4.7

「授权使用」和「复制」是两件事

中

运营商拿到工厂产品，应该只是引用（价格、图片、销售规格），不是复制出一份自己的产品。一旦复制，配方改动无法同步、数据会漂移，后面很难治理。这条要在权限文案上写清楚：授权 ≠ 复制。

05

需要你拍板的四个决策

这四个不定，研发做出来的东西大概率要返工。

1. 运营商能不能看到配方明细？
建议默认看不到，只给「成品规格 + 出杯参数」。配方明细按需单独授权，且授权只给「使用」不给「查看与导出」。
2. 平台侧（root）默认能不能看配方？
建议默认脱敏，查看需二次确认并全程审计；比「默认可见 + 事后追责」更容易通过客户的安全评审。
3. 产品授权是授给「租户」还是授给「机器」？
建议一期授给租户（简单、好解释），二期再细化到机器。直接做机器级会让「转移后产品清单」变成必填项，复杂度翻倍。
4. 「全部品牌」是否包含未来新增的品牌？
建议只包含当前全部，新增品牌需显式授权。否则产品可见范围会随品牌库增长自动扩大。
06

上线前验收清单

用两个租户 + 一个平台账号跑这张矩阵，每格都要有明确结论。

租户 A 的用户在产品列表看不到租户 B 的任何产品，搜索关键词也搜不到研发自测
导出 Excel 的条数与列表一致，不含其他租户数据；导出的文件带租户标识研发自测
机器绑定产品时的下拉选择器只出现本租户可用产品研发自测
权限模板复制到另一租户后，机器/数据范围被重置为待指定，且保存前有校验产品验收
机器所有权转移后：产品授权随机器走、原工厂只读、目标租户机器上商品仍可售产品验收
收回品牌授权后：相关产品不可新增绑定，已上架机器有明确提示产品验收
平台远程托管进入租户后，配方页有二次确认与审计记录，导出被限制安全 / 产品
存量数据归属补齐完成，未归属清单已人工确认清零数据
