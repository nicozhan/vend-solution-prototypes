01

设计判断

先看这一节

确认书里说的「组件」，和现在后台里的「组件」不是同一种对象。现在的组件是执行部件（上水水泵、左搅拌器、磨豆电机），带一张「数据点」表；确认书里的 5 个组件是控制参数的分组容器（进水与流量、气泵与气动、搅拌、升降、清洁），底下挂的是 36 项可读写的设备参数。

判断一

组件分三类，不要混成一张表

控制组件（有参数、可下发）、执行部件（有型号/通道、可能没有控制器）、传感器定义（只读）。三者复用同一个「组件」外壳，但字段集和权限不同。

判断二

参数「定义」与「值」必须分层

组件只定义参数 schema（类型/单位/范围/权限/生效方式），型号存默认值与覆盖，设备存生效值。否则 5 个组件被 6 个型号复用时，36 项参数会被复制 6 份。

判断三

118 项工艺参数不是组件参数

它是「一杯饮品怎么做」的流程脚本，属于配方，不属于任何控制组件。混进组件参数表，会让「设备能力」和「饮品配方」互相污染，版本也无法独立演进。

1.1 一句话方案

在现有「品牌型号与组件」模块内，把组件升级成带类型、带参数组、带版本的对象；新增「型号参数配置」承接型号级覆盖；配方作为独立模块只引用型号，不进组件。设备实例（机器详情）后续只读展示「生效值 + 下发状态」。

// 三层值，越靠右优先级越高
组件定义（参数 schema + 默认值）
   └─ 型号参数（继承 + 覆盖）        ← 本次 P0
        └─ 设备参数（设备级覆盖 + 生效值）  ← P1

配方 Schema（118 参数 × 7 阶段）
   └─ 配方（12 组值）→ 型号绑定 → 设备当前配方版本
i

这套分层不是为新设备特设的。现有「上水水泵 / 磨豆电机」这类部件组件继续按原样存在，只是列表里多一个类型列；新设备建 5 个控制组件即可，两者可以挂在同一个型号下。

2.2 确认书要求 vs 现有能力

确认书要求现有能力差距优先级
5 个控制组件、36 项参数组件可建，但参数只能建成「数据点」数据点语义是「可观测」，没有读写权限、生效方式、下发反馈；需要独立的参数对象P0
每参数 12 个字段（3.6 节）约 10 个字段，且都偏遥测缺：读写权限、生效方式、适用范围、指令编码/超时/重试、安全边界、确认状态、来源P0

118 参数 / 7 阶段 / 12 配方完全没有新模块：配方与工艺（列表 + 编辑器 + 导入）P0
参数值发布/版本/回滚无版本概念，编辑即生效草稿/发布、版本号、差异、回滚P0
下发与应答（8.2 节）无下发任务、状态机、超时重试、幂等P1
传感器/状态点清单（第六章）有数据点，但没有「硬件是否确认」维度加 source_status：已确认 / 待硬件确认 / 不适用，未确认不允许出现在遥测里P1
通信协议、设备身份（8.1 节）无协议映射属于设备模型，不进组件；在型号/设备维度维护P2
!

不要直接把 36 项参数塞进现有数据点表。数据点现在是「类型 + 单位 + 范围 + 默认值」，这套字段能显示参数，但表达不了「这个参数能不能远程改、改完什么时候生效、改失败怎么办」。确认书 8.2 节的要求全部落空。

4.2 组件详情 · 规格

Tab内容与规则
概览职责描述（来自确认书 3.x）、组件编码、类型、来源状态、参数统计（总数 / 已确认 / 待确认）、关联型号数、最近 3 条变更。发布按钮在此与参数 Tab 都有。
参数按参数组折叠；列可切换「基本 / 完整」：基本 = 名称/标识/类型/单位/范围/默认值；完整 = 再加读写/生效/适用范围/确认状态/操作。默认完整视图，避免为了看权限来回切。
参数编辑统一走右侧抽屉，不做行内直改。原因：参数涉及 12 类字段、有互斥校验，行内编辑会把错误藏起来。抽屉分 5 段（标识/类型校验/权限生效/下发安全/来源），底部固定「保存草稿 / 取消」。
数据点与参数物理隔离。空状态文案明确：「该组件尚未确认可读数据点。按确认书第六章，只有已安装且控制板可读的传感器才建点位。」禁止在此处「顺手加一个参数」。
适配型号型号名 / 品牌 / 指令代码 / 型号覆盖参数数 / 状态。跳转到型号参数 Tab。指令代码默认取组件参数上的 cmdCode，型号可覆盖（沿用现有 DC_CMD 机制）。
变更记录版本号、发布时间、发布人、变更摘要、字段级差异（改了哪些参数的哪个字段、旧值 → 新值）、回滚入口。回滚生成新版本，不删除历史。

4.3 参数定义字段（对照确认书 3.6）

确认书字段后台字段控件与规则必填
原始参数标识rawCode文本，创建后只读；全局唯一（同组件内）。改名需新建参数并停用旧参数，保留映射关系是

所属组件componentId创建时继承，不可跨组件移动是
参数类型dataType枚举：整数 / 小数 / 布尔 / 枚举 / 时间 / 字符串。切换类型时清空不适用的校验字段并二次确认是
单位unit + unitStatus文本 + 状态。可填「待确认」，此时单位列显示橙色，且该参数不能进入正式下发是（可为待确认）
默认值defaultValue按类型校验；布尔用开关；时间用 HH:mm；空值表示未配置，不自动补 0否
最小值 / 最大值min/max数值型必填；单位待确认时允许为空但标黄条件
步长 / 精度step/precision步长 > 0 且能整除范围；精度与步长一致（如步长 0.1 → 精度 1 位）否
读写权限rw只读 / 可写 / 仅工程师。只读参数不建下发按钮是
生效方式effectMode立即 / 下一杯 / 空闲时 / 重启后。影响下发后的确认时机与提示文案是

  • 只允许覆盖，不允许新增。型号上新增的参数无处归属，会让「组件定义」失去唯一来源。

  • 提交前做跨参数校验。例如「分段下降距离 32 × 次数 3」与「全行程行程 94」是否自相矛盾；「清洗停留时间」是否超过定时清洁窗口。这类规则先配置成提示（P0 警告），不阻断发布（P1 再升级为阻断）。
  • 发布影响面提示。发布时展示「影响 12 台设备，其中 9 台在线；3 台离线将在下次上线后同步」，不允许静默发布。
  • 导出即交付物。「导出参数表」生成一份按组件分组的 Excel/CSV，列与固件方对接表一致（标识、名称、类型、单位、范围、默认值、型号值、确认状态），可直接拿去联调。

4.5 配方模块的边界

问题设计结论原因
配方参数挂哪个组件？不挂118 项是工艺流程，跨豆仓、水路、气路、升降、清洁五个组件；挂到任一组件都会造成错误归属
配方和型号什么关系？型号绑定配方集，设备继承型号的默认配方同一型号在不同点位可能卖不同饮品，所以设备层允许换配方版本（P1）
配方要不要版本？要，与组件版本独立组件参数改的是硬件动作边界，配方改的是单杯工艺；两者发布节奏不同，不能绑在一起
空值怎么处理？未配置 = 空，不补 0，不继承确认书明确 No.5 / No.30 全配方为空；补 0 会变成一个真实的下发值
Excel 导入失败怎么办？整体不落库，给行级错误清单部分导入会造成 118 项里一半新一半旧，比导入失败更危险

交互与校验规则

会被问到的那几条

5.1 编辑 → 草稿 → 发布

编辑参数（右侧抽屉）
   └─ 保存草稿：只写 draft，不产生版本，不影响型号/设备
        └─ 发布：校验通过 → 生成 v(n+1) 快照 → 写入变更日志
             ├─ 被型号引用 → 型号页提示「组件已更新，当前型号仍用 v(n)」
             └─ 下发（P1）→ 生成 PublishJob，逐台确认
i

为什么不「保存即生效」：36 项参数里有一半是动作边界（升降行程、清洁次数），改错会直接让设备做出错误动作。草稿与发布分离，是给产线留一次「复核」的机会，也是审计的最小单位。

5.2 校验规则

规则校验内容级别
标识唯一同一组件内 rawCode 不重复；跨组件允许同名（不同固件模块可能重名）阻断
范围合法min < max；默认值落在范围内；step 能整除 (max−min)阻断
单位状态数值型参数必须有单位或显式标「待确认」；标了待确认不允许进入正式下发阻断（发布）
布尔语义布尔参数不填单位；必须填写 0/1 的语义说明（关闭/开启、禁用/启用）警告
枚举完整枚举至少 2 项，去重，默认值必须是其中一项阻断
时间格式HH:mm，24 小时制；需要明确设备本地时区还是 UTC警告
下发完整可写参数必须有 cmdCode；超时 ≥ 1s；重试 0–3 次阻断
安全边界升降 / 清洁 / 气动类参数必须填互锁条件与最大运行时长阻断
跨参数一致行程 × 次数与总行程、清洗窗口与定时清洁时间是否冲突警告
待确认门禁存在待确认项时：允许存草稿；发布需勾选「已知未确认，仅用于演示」并填写原因二次确认

9.1 会卡住设计的 6 个问题

问题为什么卡不确认时的临时方案
升降类参数的单位与范围距离 / 行程 / 速度共 9 项，全部「待确认」；没有范围就无法做上下限校验范围留空 + 强制待确认标记，发布只能标「演示」
Dclean_interval_time 的 12 是什么小时 / 天 / 次数会直接影响界面的单位与校验显示「12（单位待确认）」，不参与任何换算
0/1 的语义两个使能参数若语义反了，下发会得到完全相反的效果界面上写成「0=关闭 / 1=开启（待确认）」，不允许只显示数字
定时清洁的时区设备本地时间 / UTC / 服务器时间，决定「10:00」的含义按设备本地时间处理，页面明确标注
批量写入与回滚能力决定下发是「逐项」还是「整套」，也决定失败恢复策略P0 只做逐项模拟；P1 按实际协议实现
No.114 / No.117 的 g 是否为笔误若是时间，校验规则完全不同保留原文，标「单位待确认」，不做数值校验

9.2 风险

风险影响应对
组件边界与客户硬件不一致5 个组件是按参数表归类的建议值，客户实际可能是 8 个控制器组件编码与固件模块解耦；支持后续拆分/合并并保留参数迁移记录
参数被当成「传感器」展示运营看到「进水量 140」会以为是实时读数参数 Tab 与数据点 Tab 物理隔离；参数页标注「配置值，非实时测量」
配方与组件版本互相牵连改一个组件参数导致所有配方需要重新验证版本独立；发布时只提示「受影响配方」，不自动升版
确认状态被随手点成「已确认」门禁形同虚设确认需填写依据（文档页码 / 邮件 / 实测记录），并记录确认人

9.3 下一步建议

  1. 先把 5 个控制组件 + 36 项参数按本文模型录进原型，确认「组件—参数—型号」三层的交互是否顺手。
  2. 拿「清洁系统控制」做一条完整样例：建组件 → 录 21 项 → 型号覆盖 2 项 → 模拟下发 → 查看失败重试。
  3. 把导出的参数表直接发给客户固件方，让他们按表填单位、范围、读写与生效方式——这张表就是最省事的确认书。
  4. 等客户回填后再决定配方是否进入编辑态：单位没定之前，编辑只会制造错误数据。
